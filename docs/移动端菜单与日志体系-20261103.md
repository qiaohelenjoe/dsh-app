# 移动端菜单精简与日志体系方案（2026-11-03）

## 1. 背景与目标

DSH 移动端（Flutter WebView 壳）当前直接加载桌面版 DSH Web UI。左侧面板由 DSH 把已安装插件平铺出来，手机上菜单过多、挤压功能区。前期采用“黑名单隐藏若干菜单”的方式，覆盖不了后续新增插件。

本次目标：

1. 移动端侧栏改为**白名单 + 统一「更多功能」入口**：不在白名单内的插件入口全部收起，点击「更多功能」弹出菜单，再进入具体插件。
2. **调试入口分构建形态**：测试包显示 🐞 诊断按钮，生产包不显示。
3. **建立移动端日志体系**：App 采集启动/登录/网络/WebSocket/页面错误等日志，脱敏后上传服务端，服务端可按账号、设备、时间、`requestId` 直接定位问题；先用 SQL/CLI 查询。
4. 配额按账号配置（PC 2 台 / 移动 3 台）已在 2026-10-30 上线，本文档一并记录。

## 2. 现状与已完成的修复

- DSH Web UI 只支持**根路径**。服务端用 `dsh_device` Cookie 选择设备，`dsh_access` Cookie 维持登录，代理 `/`、`/api/*`、`/assets/*`、`/plugins/*` 与插件根路径（`/dsh-whale`、`/dsh-market`、`/mcp-connector`、`/open-in-app`、`/bsk-observation`）。
- 手机旧 WebView 缺少 `Promise.withResolvers`、`AbortSignal.any` 等 API，导致 DSH 连接恢复崩溃、WebSocket `4000 reconnect requested` 循环。已在代理返回的 HTML `<head>` 注入 polyfill 修复。
- 设备配额已改为按账号：`accounts.desktop_device_limit` 默认 2、`mobile_device_limit` 默认 3；设备注册、登录、网页登录创建设备均校验配额，同名称+平台复用设备。
- 移动端已注入 `data-dsh-mobile-app=1` 标记，客户端插件识别后不显示「移动端」入口。

## 3. 移动端菜单设计

### 3.1 保留项（白名单）

系统项：

- 新建会话
- 收起侧边栏
- 搜索会话
- 视图选项
- 添加工作区
- 账号菜单

业务项：

- 会话
- 自动化任务
- 工作区
- 设置

### 3.2 收起项

其余侧栏插件入口全部收起，包括但不限于：

- 插件
- 移动端（任何时候都不显示）
- 插件市场
- 记忆系统
- SSH
- MCP 连接器
- 后续新安装的插件

### 3.3 「更多功能」入口

- 在侧栏固定位置插入「更多功能」入口（图标 + 文字）
- 点击弹出底部菜单，列出所有被收起的插件名称
- 点击某一项：触发原入口的 `click()`，复用插件原有行为；菜单关闭
- 原入口仅隐藏，不卸载、不禁用
- DSH 自带的「更多」保持原样
- PC 端（非 App 内）完全不受影响

### 3.4 实现要点

- 客户端插件在 `mobile` 模式下扫描左侧区域的可点击项（`button/a/[role=button]`），按 `aria-label`/文本匹配白名单
- 白名单之外：`display:none`，并记录原始元素引用
- MutationObserver 监听侧栏重渲染，重新应用策略并补回入口
- 使用 `data-dsh-mobile-app=1` 判断是否 App 内，折叠屏展开/横屏同样生效

## 4. 测试包 / 生产包

- 通过 Flutter `--dart-define=DSH_DEBUG_UI=true` 构建测试包：显示 🐞 诊断按钮、上传全量日志
- 生产包不传该参数：不显示调试入口，只上传 `warn/error` 与崩溃日志
- 两个 APK 均使用同一版本号规则，文件名区分：
  - `dsh-mobile-<version>.apk`（生产）
  - `dsh-mobile-<version>-test.apk`（测试）

## 5. 日志体系

### 5.1 App 采集

- 启动、登录/刷新会话、设备选择、页面导航
- 网络请求：方法、URL 路径、状态码、耗时、错误摘要（不记录请求体）
- WebSocket：打开、关闭码、原因
- 页面 console：level + message
- 未捕获异常

采集实现：

- 页面侧网络探针：代理在 HTML 注入脚本，记录 `window.__dshNetLog`（fetch/XHR/WS 元数据，最多 200 条）
- App 侧 `AppLogger`：环形缓冲 500 条，级别 `debug/info/warn/error`
- 脱敏：token、Cookie、Authorization、password、secret 一律丢弃；URL 中的 `token` 查询参数剥离

### 5.2 上报策略

- 测试包：全部级别
- 生产包：`warn/error`（含崩溃）
- 触发：出现 error 立即批量上报；其余每 60 秒；App 退后台前 flush
- 批量 ≤50 条/次，失败指数退避重试，不阻塞 UI
- 接口：`POST /v1/client-logs`，Bearer 访问令牌

### 5.3 服务端存储

新表 `client_logs`：

| 字段 | 说明 |
|---|---|
| id | bigserial 主键 |
| account_id | 账号 ID |
| device_id | 设备 ID（可空） |
| app_version | App 版本 |
| platform | android/ios |
| level | debug/info/warn/error |
| event | 事件名，如 `startup`、`api_error`、`ws_close` |
| message | 摘要（≤2KB） |
| context | jsonb（脱敏后，≤4KB） |
| request_id | 服务端错误响应中的 requestId，便于关联 |
| created_at | 时间 |

- 索引：`(account_id, created_at desc)`、`(created_at)`
- 保留期：30 天，服务端定时清理

### 5.4 接口契约

`POST /v1/client-logs`

```json
{
  "appVersion": "0.1.12",
  "platform": "android",
  "entries": [
    {
      "level": "error",
      "event": "api_error",
      "message": "POST /api/session/list -> 504",
      "requestId": "req-abc",
      "context": { "status": 504, "ms": 60001 }
    }
  ]
}
```

- 鉴权：Bearer access token
- 批量上限 100 条，单条 message ≤2KB，单请求 ≤64KB
- 限流：每账号 120 次/分钟
- 返回：`202 { accepted: n }`

### 5.5 查询（SQL/CLI）

按账号与时间：

```sql
SELECT created_at, level, event, message, request_id, context
FROM client_logs
WHERE account_id = '<account-uuid>'
  AND created_at > now() - interval '2 hours'
ORDER BY created_at DESC
LIMIT 200;
```

按 `requestId` 关联服务端请求：

```sql
SELECT * FROM client_logs WHERE request_id = 'req-xxxx';
```

按设备：

```sql
SELECT * FROM client_logs
WHERE device_id = '<device-uuid>'
ORDER BY created_at DESC LIMIT 200;
```

服务器上执行：

```bash
cd /opt/dsh-account/deploy
docker compose exec -T db psql -U dsh -d dsh_account -c "<SQL>"
```

## 6. 验收标准

1. 手机 App 内左侧只看到白名单项 +「更多功能」；点击「更多功能」能看到被收起的插件并可进入；PC 端不变。
2. 测试包有 🐞，生产包没有 🐞。
3. 手机产生错误后，服务端 `client_logs` 可查到对应记录，包含 `requestId`，且无 token/Cookie/请求体。
4. 服务端测试全绿；插件 `check:client` 通过；Flutter `analyze` 无问题且测试全绿。
5. 生产部署前完成数据库与代码备份。

## 7. 实施步骤与文件

1. 客户端插件：`plugin/src/client.ts`（白名单 + 更多功能 + 观察器）
2. 服务端：`server/migrations/0003_client_logs.sql`、`server/src/http/client-log-routes.ts`、`app.ts` 注册、30 天清理
3. 服务端测试：上传/脱敏/鉴权/限流
4. App：`mobile/lib/logging.dart`、`webview_page.dart`（调试按钮开关、日志接入）、`api.dart` 上报
5. 打包：测试包（`DSH_DEBUG_UI=true`）与生产包
6. 部署：备份 → 迁移 → 上线 → 验证

## 8. 部署、备份与回滚

- 备份：`pg_dump` 全库 + `accounts` 表 + 当前 `server/src`、`plugin`、`mobile` 代码 tar
- 部署：`docker compose build server && docker compose up -d server`
- 插件：同步到 desktop profile 后重启 DSH
- 回滚：恢复代码备份 + 数据库备份；迁移只新增表/列，回滚可保留数据

## 9. 风险与后续

- DSH 侧栏 DOM 结构可能随版本变化：使用多选择器与 MutationObserver 兜底，插件升级后需回归测试
- 日志上传依赖网络：失败重试且不影响主流程；生产只传错误级控制体积
- 管理页面暂不做，用 SQL/CLI；后续可按需加只读管理接口
- iOS 构建仍需 macOS/CI；正式签名待后续

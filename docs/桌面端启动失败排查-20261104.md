# DeepSeek Harness 桌面端启动失败排查（2026-11-04）

## 1. 现象

- 启动 DeepSeek Harness 桌面端后进程几秒内退出，界面不出现。
- 崩溃日志目录 `%APPDATA%\@deepseek-ai\dsh-desktop\logs` 持续生成 `crash-*-host.log`，内容固定为：

```
Error: desktop welcome: Web authentication failed
    at connectDesktopWelcome (...)
```

- 时间点：2026-11-04 09:38 起每次启动必现（此前 09:37 应用仍正常运行）。
- 诱因猜测：当天 09:28 曾用自定义文件资源管理器 provider 替换官方实现并重新安装插件，因此最初怀疑是插件改动导致。

## 2. 排查过程

1. **先撤销可疑改动**：移除 `plugin/src/client.ts` 中自实现的 `file` resource provider，移除 `server/src/http/proxy.ts` 对官方 workspace-files bundle 的 inject 改写，回退对应测试，重建并同步到桌面 profile。
   - 结果：应用**仍然启动失败**，错误完全一致 → 说明 provider 不是启动失败原因。
2. **确认宿主侧正常**：用 Electron node 模式直接拉起 `dsh-desktop-host`（`resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-desktop-host/lib/index.js`），宿主打印 launch URL，用带 cookie 的请求访问 `/` 返回 **200**（页面 38,703 字节）→ 宿主与插件都正常。
3. **定位到桌面壳的认证环节**：桌面壳启动流程为
   - `host.start()` → 拿到 `http://127.0.0.1:<port>/?token=...`
   - `authenticateWebHost(url)` → 普通请求拿到 303 + `set-cookie`
   - `connectDesktopWelcome(url, net.fetch, credentials: "include")` → 由 Chromium 网络栈发出，**会带上 127.0.0.1 的全部 cookie**
4. **检查 Chromium cookie 库** `Network/Cookies`（SQLite）：
   - `host_key=127.0.0.1` 下共 **71 条** `dsh-auth-*` cookie，创建时间从 2026-10-17 一直到当天；
   - 每条约 230 字节，Cookie 头合计 **16,186 字节**；
   - 这些 cookie 全部是持久化的（`is_persistent=1`），每次启动新宿主都会新增一条随机名 cookie，且从不清理。
5. **实测复现**（对真实宿主发请求）：

| 请求 | Cookie 头 | 结果 |
|---|---|---|
| `/` + 仅 1 个本次有效 cookie | ~230 B | 200 |
| `/` + 库中全部旧 cookie | 16,186 B | 401 |
| `/` + 全部旧 cookie + 本次有效 cookie | **16,414 B** | **431 Request Header Fields Too Large** |

Node HTTP 服务默认 `maxHeaderSize` 为 **16,384 字节**，Cookie 头超过该上限时宿主直接返回 431，桌面壳判定响应非 2xx → 抛出 `Web authentication failed`。

## 3. 根因

**不是业务代码/插件问题，而是 DSH 桌面端自带的认证 cookie 泄漏并累积，最终撑爆请求头大小限制。**

- 桌面端每次启动为本地宿主生成一条随机命名的 `dsh-auth-<random>` cookie，作用域 `127.0.0.1`（cookie 不区分端口），持久化保存且不回收；
- 多次启动后 cookie 条数线性增长，Cookie 请求头随之增长；
- 当天累计到 71 条、16.4 KB，越过 16 KB 上限；
- 超过上限后每次启动都失败，且每次失败又新增一条 cookie，形成"越失败越多、越多越失败"的自我恶化循环。

09:28 的插件安装只是让应用发生了一次重启，**恰好触发已接近临界值的 cookie 头**，因此故障时间点与插件改动重合，属于误导性相关。

## 4. 修复动作

- 备份 cookie 库：`Network/Cookies` → `Network/Cookies.bak-20261104022845`（同目录，带时间戳）
- 仅删除 `host_key=127.0.0.1` 且 `name LIKE 'dsh-auth-%'` 的记录（共 71 条），其他站点/其他 cookie 未动
- 重启验证：应用正常启动，主窗口出现，无新增崩溃日志

## 6. 复发风险与建议

- 每次启动仍会新增一条 `dsh-auth-*` cookie（约 230 字节），按当前规模约再启动 60 余次会再次触顶。
- 临时规避（应用完全退出后执行，先备份 `Network/Cookies`）：只删除 `127.0.0.1` 下的 `dsh-auth-*` 记录，不要在应用运行时改库。
- 建议向 DSH 反馈：桌面端应在每次启动复用同一个 cookie 名，或在退出/崩溃恢复时清理旧 `dsh-auth-*`；宿主若能把 `maxHeaderSize` 提到 32 KB 也可显著缓解。
- 排障经验：本次崩溃信息 `Web authentication failed` 指向本地回环认证，与被测业务插件无关；遇到桌面端"认证失败"类启动问题，优先检查 `Network/Cookies` 的条数与体积，而不是先怀疑业务代码。

## 7. 日常维护脚本（2026-11-04 追加）

`deploy/clean-dsh-auth-cookies.mjs` 用于定期清理累积的 `dsh-auth-*`。

**必须在 DeepSeek Harness 完全退出后执行**（含托盘图标）。Chromium 运行期间独占
`Network/Cookies`：只读打开会报 `unable to open database file`，复制会 `EBUSY`。

```bash
# 只看条数，不修改
node deploy/clean-dsh-auth-cookies.mjs --dry-run

# 备份（Cookies.bak-<时间戳>）后清理 127.0.0.1 下的 dsh-auth-*，并 VACUUM
node deploy/clean-dsh-auth-cookies.mjs
```

- 只删除 `host_key = '127.0.0.1' AND name LIKE 'dsh-auth-%'`，其他站点与其他 cookie 一律不动
- 建议在条数接近 50 时清理一次，或每月例行执行
- 复发周期约 60 次启动（每次新增 1 条约 230 B，上限 16 KB）
- 脚本依赖 Node 22 内置的 `node:sqlite`（实验特性，会打印 ExperimentalWarning，属正常）
